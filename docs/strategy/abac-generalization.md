# ABAC Generalization — data-driven route policies (analysis)

> Analysis only. No source was modified. Every claim below is traceable to `file:line` in this repo (or, for the reference comparison, in `/Users/ankurpandey/Documents/GitHub/oe_core`).
> New-engineer orientation: read `aegis/ONBOARDING.md` and `docs/03-access-control-model.md` first. This document is the build spec for turning the *dormant* persisted ABAC `policies` table into a live, data-driven authorization layer. It is the single source of truth for that build.
> Revision note: this version incorporates a red-team review. The load-bearing corrections: the policy read must work in **every service process**, not just user-management (§1.1, §2.2, Q6); the cache convergence bound is made real via **versioned keys** (Q4/Q5); the mapper is **all-or-nothing** for both effects (Q1/Q8); a **cross-attribute comparison capability** now gates helper retirement (Q3, §5 Phase 5); the v1 rule envelope **drops `scope`** (Q1); and the lazy PIP is fully specified (Q10, §5 Phase 2).

---

## 0. Verdict — does it add value? is it feasible?

**Yes on both — with one load-bearing prerequisite (a PIP that populates `principal.attributes`) and one topology constraint that shapes all the wiring (the policy read must be available in every consuming service process, §2.2).**

- **Value: high leverage, low new surface.** The full ABAC machinery already exists and is well-factored — a PDP with deny-overrides (`libs/access-control/src/pdp.ts:17-100`), a generic condition evaluator with 11 operators and dotted attribute paths (`libs/access-control/src/condition-evaluator.ts:4-76`), a resource-agnostic row-scope layer (`libs/access-control/src/scope.ts:14-41`), a persisted, RLS-isolated, tenant-owned `policies` table with full PAP CRUD (`apps/cli/src/migrations/0028_identity_admin_surfaces.ts:30-50`; `apps/user-management/src/controllers/policy.controller.ts:16-39`), and a Redis reload bus for Casbin (`libs/access-control/src/watcher.ts:30, 97-105` — though ABAC v1 deliberately does **not** depend on it, Q5). The **only** missing seam is a loader that reads persisted rows into `AccessShape.PolicyRule[]` and hands them to `authorize()` — the loader docs already describe this as the intended plug-in point ("A DB-backed loader (policies persisted via the PAP) plugs in by returning the fetched rules from an async function with the same signature", `libs/access-control/src/policy-loader.ts:28-29`). Today runtime ABAC is 100% hardcoded: the *single* wired loader is `amountCapPolicies` (`policy-loader.ts:62-75`) on exactly two expense routes (`apps/expense/src/controllers/expense-report.controller.ts:91, :119`). Persisted policies are administered but **never read** by enforcement — nothing outside user-management's own CRUD touches `TableName.Policies`. Closing that gap turns a write-only admin surface into working, tenant-authored, no-deploy authorization.

- **Feasibility: high.** No schema redesign is required for v1 (§3, Q2). The bridge is a pure mapper + a cached async loader + one PAP-side invalidation call. Casbin RBAC, RLS, and the PDP evaluation semantics are untouched in v1. Two capabilities are **not** in the current evaluator/loader and are scheduled explicitly: attribute-to-attribute comparison (needed before the hardcoded helper can be retired — §3 Q3, §5 Phase 5) and the PIP hook in the PEP (§3 Q10, §5 Phase 2).

- **THE load-bearing prerequisite — a PIP (Policy Information Point).** The login token carries **no** `attributes` field at all: `AuthService.login` assembles claims as only `{sub, tenant_id, roles, permissions, scope, aud}` (`apps/user-management/src/services/auth.service.ts:54-61`), `getAccess` returns only `{roles, permissions, scope}` — it never queries `TeamMember` and there is no approval-limit column or lookup anywhere (`apps/user-management/src/repositories/user.repository.ts:95-112`), and the typed `JwtClaims` has no `attributes` member (`libs/shared/types/src/user-management.shape.ts:478-485`). The PEP pipe exists (`AegisJwtClaims` declares `attributes?`, `pep.ts:28`; principal assembly copies it at `pep.ts:60`) but since no issuer ever writes it, **`principal.attributes` is always `undefined` in production**. Consequence: both attribute-dependent ABAC features are wired but **silently no-op** — the amount cap never denies (`policy-loader.ts:64-65` returns `[]` when `approvalLimit` is absent, so RBAC alone decides and an approver can approve *any* amount), and `own_and_team` degrades to owner-only (`scope.ts:32-33` reads `attributes?.['teamIds'] ?? []`, always empty). **Any DB-backed ABAC policy that references a principal attribute is inert until the PIP ships.** The PIP is therefore in-scope for this project, not adjacent (§3 Q10, §5 Phase 2 — including *where* it hooks into the PEP and *how* it reads identity tables from non-identity services).

## 1. Current-state summary

### 1.1 The decision pipeline (two sequential, fail-closed gates)

Every protected route is `authenticate(), authorize(Permission.X, opts)`; `authorize(action)` delegates to `authorizeAny([action])` (`libs/access-control/src/pep.ts:243-245, 248`).

| Stage | What it does | Where |
|---|---|---|
| `authenticate()` | Verify HS256 JWT (`AUTH_JWT_SECRET`); assert token `tenant_id` == request-context tenant; build `req.principal` = `{userId, tenantId, roles, permissions?, scope?, attributes?}` from claims | `pep.ts:36-67` (principal at :54-61) |
| **Gate 1 — Casbin RBAC** | subjects = `[...principal.roles, principal.userId]`; `firstAllowedAction` iterates actions×subjects calling `enforce(subject, tenantId, action)`; no grant ⇒ 403; winning permission saved to `res.locals.authorizedPermission` | `pep.ts:261-270, 214-228` |
| Casbin model | RBAC-with-domains, `dom = tenantId`; matcher `(r.sub==p.sub \|\| g(r.sub,p.sub,r.dom)) && (p.dom==r.dom \|\| p.dom=="*") && r.act==p.act`; effect `some(where p.eft==allow)` | `libs/access-control/src/enforcer.ts:21-36` |
| **Gate 2 — PDP (ABAC + scope)** | Runs **only** when the route supplies `resource:` and/or `policies:` loaders (`pep.ts:273-275`). Branch: `principal.permissions` non-empty ⇒ `decide()`; else ⇒ `evaluateAbac()` (W5-04 Casbin-authoritative path). Deny ⇒ 403 with the PDP reason; allow ⇒ `res.locals.obligations = decision.obligations ?? []` | `pep.ts:273-290` (branch at :281-284, obligations at :288) |

The composition seam (`pep.ts:281-284`):

```ts
const decision =
  principal.permissions && principal.permissions.length > 0
    ? decide({ principal, action: allowedAction, resource }, policies)
    : evaluateAbac({ principal, action: allowedAction, resource }, policies);
```

Infrastructure facts that constrain the design:

- **Deployment topology: one process per service, one shared Postgres.** `docker-compose.all.yml` builds a **separate image per service** and runs each as its own container: gateway reverse-proxies on 4000 (`:80-86`), user-management on 4001 (`:88-94`), expense on 4002 (`:96-102`), payroll on 4003 (`:104-110`), invoice on 4007 (`:153-159`). `dbPolicies` executes inside `authorize()` **in the consuming service's process** — anything registered only in user-management's bootstrap simply does not exist in the expense/invoice/payroll processes. What makes the design feasible anyway: **all services point at the same Postgres** (identical `DATABASE_URL` in every `apps/*/.env:10`, `aegis_app@postgres:5432/aegis`) under RLS, and the repo already has a sanctioned cross-domain read pattern — a shared lib defining models/queries on the shared connection: expense's bootstrap calls `getApprovalContext()` from `libs/approvals` (`apps/expense/src/bootstrap.ts:31-32`; `libs/approvals/src/models/database-context.ts:31-48`), and `libs/db` ships a **model-free raw-SELECT reader** precedent (`libs/db/src/feature-flags-reader.ts:19-29` — parameterized SQL inside `withTenantTransaction`, `libs/db/src/transaction.ts:10-20`). §2.2/Q6 build on exactly these two patterns.
- **Casbin layer cannot express deny.** Effect is allow-if-any-allow (`enforcer.ts:32`); a `p`-row with `eft='deny'` is inert. **All deny semantics live exclusively in the PDP**, which only runs when a route supplies `resource:`/`policies:` options. A route without those options is RBAC-only.
- **Fail-closed everywhere:** `enforce()` returns false on any throw (`enforcer.ts:103-114`); `reloadEnforcer` clears the in-memory policy on reload failure so the pod denies everything until a healthy reload (`pep.ts:124-148`); checks are serialized against reloads/grants via the `withPolicyOperation` mutex (`pep.ts:77-89`).
- **Error semantics of a throwing loader:** `authorizeAny` catches any throw and `next(err)`s (`pep.ts:294-296`); the terminal error middleware wraps non-AppErrors as `ErrUtils.system` ⇒ **HTTP 500 with a generic client message** and full server-side log (`libs/service-core/src/middleware/error.middleware.ts:31-33, :53`). So "loader throws" blocks the request (fail-closed in effect) but reads as **5xx, not 403** — the design adopts this as the deliberate contract (Q4): 403 = "you may not", 5xx = "cannot decide" (infra outage). Ops triage and the §6 tests assert accordingly.
- **Cross-pod freshness (RBAC only today):** `applyPolicyGrant` writes p/g rows through the adapter (revokes before adds, BUG-0008) then calls `invalidatePolicies()` which publishes on Redis channel `aegis:access-control:policy-reload` (`pep.ts:188-202`; `watcher.ts:30, 97-105`). The ABAC PAP publishes **nothing** (§1.4). Note for later phases: the watcher is single-channel and single-handler, its payload is a bare timestamp (`watcher.ts:100`), and it is **fail-open at startup with no retry** — a pod that boots during a Redis outage never subscribes even after Redis recovers (`watcher.ts:74-81`; `state` stays undefined so `invalidatePolicies` returns 0, `:98`). ABAC v1 sidesteps all of this by not using pub/sub (Q5).
- Casbin RBAC rows are persisted (Postgres `casbin` table via casbin-pg-adapter on `DATABASE_URL`, migration 0009, seeder 0003) and loaded once per process with caching (`enforcer.ts:69-80`; `pep.ts:73-114`).

### 1.2 PDP internals — evaluation order and effect combination

`decide()` (`pdp.ts:17-54`): (1) RBAC membership — `req.action ∈ principal.permissions` (`pdp.ts:24`); (2) tenant isolation — `resource.tenantId`, when present, must equal `principal.tenantId` (`pdp.ts:29`); (3) **deny-overrides** — linear scan; the first `deny` rule whose `action` equals the request action or `'*'` and whose conditions all match denies with reason `denied by policy ${p.id}` (`pdp.ts:34-38`); (4) row scope via `checkRowScope` (`pdp.ts:41`); (5) **allow-policy gating** — if allow rules exist for the action, ≥1 must have all conditions match, else deny `'no allow-policy condition matched'` (`pdp.ts:47-50`); (6) otherwise allow. `evaluateAbac()` (`pdp.ts:70-100`) is identical minus step 1.

- **Deny-overrides is absolute and order-independent:** any matching deny wins regardless of any allows; there is no sort, and array order only affects *which* deny's id appears in the reason, not the outcome (`pdp.ts:34-38, 80-84`).
- **Allows are a gate, never an override:** with zero policies, the gate is vacuous and the PDP reduces to tenant-isolation + row-scope. **Corollary (load-bearing for Q1/Q8): dropping allow rows also fails open** — if a loader silently loses the last allow row for an action, `allowPolicies` is empty and the gate vanishes (`pdp.ts:47-50, 93-97`); a route that was gated ("payroll sensitive read only when X") becomes unconditionally allowed to anyone passing RBAC.
- **No priority anywhere in the runtime path:** `AccessShape.PolicyRule` = `{id, tenantId?, effect: 'allow'|'deny', action: Permission|'*', conditions?, scope?}` — **no `priority` field** (`libs/shared/types/src/access.shape.ts:59-66`). Priority exists only on the persisted (never-loaded) PAP rows. See §3 Q8.
- **`PolicyRule.scope` is dead code:** the shape declares `scope?: Scope` (`access.shape.ts:65`) but **nothing in the runtime consumes it** — neither `decide()` nor `evaluateAbac()` ever reads `p.scope`, and `checkRowScope` reads only `principal.scope` (`scope.ts:18`). A persisted rule carrying `{"scope": "own_only"}` would get zero enforcement, silently — exactly the administered-but-inert failure class §1.6 condemns. §3 Q1 therefore **bans `scope` from the v1 rule envelope**.
- **Subtle divergence:** `decide()`'s allow-gating filter matches only `p.action === req.action` (`pdp.ts:47`, ignores `'*'`); `evaluateAbac()`'s honors `'*'` too (`pdp.ts:93`). A wildcard-action *allow* policy gates Casbin-only principals but is invisible to permissions-carrying principals. **A generalized loader must not depend on this difference** (§7).
- **A second decide-vs-Casbin divergence matters for rollout:** `decide()` step 1 re-checks the **JWT `permissions` array** (`pdp.ts:24`). Wiring `dbPolicies` (or any `policies:`/`resource:` option) onto a currently RBAC-only route *activates Gate 2*; a permissions-carrying principal whose token predates a runtime Casbin grant will then 403 where Casbin alone allowed, until re-login refreshes the claims. Flagged per-adoption in §3 Q9 and §6.
- **Obligations are dead code today:** `pep.ts:288` copies `decision.obligations` to `res.locals`, but neither `decide()` (`pdp.ts:53`) nor `evaluateAbac()` (`pdp.ts:99`) ever *returns* obligations — `evaluateAbac` even computes `matchingAllow` (`pdp.ts:94`) then discards it. Column-masking obligations described in `access.shape.ts:39-43` require a small PDP change to actually flow (§5 Phase 4).

### 1.3 Condition evaluator + row scope

- `conditionsMatch` is AND-semantics; empty/undefined conditions ⇒ vacuously true (`condition-evaluator.ts:70-76`).
- `evalCondition` resolves `cond.attribute` as a dotted path via `resolveAttr` rooted at `principal.` / `resource.` / `environment.` / the literal `action`; at every hop it transparently falls through into an `attributes` bag, so `principal.approvalLimit` and `principal.attributes.approvalLimit` both resolve (`condition-evaluator.ts:4-29`, bag fall-through at :26). Unknown root ⇒ undefined.
- Operators: `eq` (strict `===`), `neq`, `lt/lte/gt/gte` (Number-coerced), `in`, `contains`, `owner` (`resource.ownerId === principal.userId`), `manager_of` (`principal.attributes.managerOf` includes `resource.ownerId`), `tenant_match`. **Unknown operator ⇒ false (fail-closed)** (`condition-evaluator.ts:39-66`).
- **Conditions compare against LITERALS only.** Every operator compares the resolved left side to `cond.value` as a literal — the ordered operators call `asNumber(value)` on the rule's stored value (`condition-evaluator.ts:44-51`). There is **no attribute-to-attribute operator**: no persisted rule can express `resource.amount > principal.approvalLimit`. `amountCapPolicies` only works because it *synthesizes* the rule per request with the principal's cap baked into `value` (`policy-loader.ts:62-75`). This is the single evaluator/loader capability gap in the whole design — §3 Q3 defines the `$attr` reference convention that closes it, and §5 Phase 5 (helper retirement) is **blocked** on it.
- **`environment.*` is unusable today:** `AccessRequest.environment` exists in the shape (`access.shape.ts:35`) and `resolveAttr` supports the root, but the PEP builds requests as `{principal, action, resource}` only (`pep.ts:283-284`) — any `environment.*` condition silently resolves undefined. See §3 Q3.
- `checkRowScope` (`scope.ts:14-41`): no resource (collection call) / no `principal.scope` / `Scope.AllRecords` ⇒ ok; `OwnOnly` ⇒ `resource.ownerId === principal.userId`; `OwnAndTeam` ⇒ owner **or** `resource.teamId ∈ principal.attributes.teamIds` (`scope.ts:30-38`). **Any unrecognized scope value falls through to `{ok: true}` — fail-open** (`scope.ts:40`). Scope enum values: `all_records / own_and_team / own_only` (`libs/shared/enums/src/access.enum.ts:100-104`). Note: `checkRowScope` runs **inside** the PDP (`pdp.ts:41, :87`), which fixes where the PIP must have populated attributes by (§3 Q10).
- **List filtering is NOT in this library.** `rowScopeSubmitterFilter()` is a private helper in `apps/expense/src/services/expense.service.ts:1008-1014` (used at :338): Admin/Owner/Manager/Approver get no filter (see all); everyone else is constrained to `submitterId = currentUserId` in SQL. It keys off **role names** from `RequestContext`, not `principal.scope` — a `scope=own_only` principal holding the Manager role still sees all rows on list routes.

### 1.4 The persisted `policies` table + PAP API (administered but DORMANT)

- **DDL** (`apps/cli/src/migrations/0028_identity_admin_surfaces.ts:30-50`): `id` (UUID PK), `tenant_id` (UUID NOT NULL, FK→tenants ON DELETE CASCADE), `permission` (STRING NOT NULL — **free string**, not enum/FK-checked), `effect` (STRING NOT NULL, default `'allow'`, CHECK `policies_effect_chk` pinning to `'allow'/'deny'`, :45-50), `rule` (JSONB NOT NULL, default `{}`), `priority` (INTEGER NOT NULL, default 100), `is_active` (BOOLEAN NOT NULL, default true), `created_by/updated_by`, `deleted_at` (soft delete), timestamps.
- **Indexes:** `(tenant_id, permission)` and `(tenant_id, priority)` (`0028:43-44`).
- **RLS:** ENABLE + FORCE, plus a RESTRICTIVE `policies_tenant_isolation` policy on the transaction-local tenant setting — applied at `0028:111-117` via `rlsPolicyStatements` (`libs/db/src/rls.ts:38-54`). Rows never cross tenants at the Postgres layer.
- **Model:** paranoid (soft delete), `rule` is untyped JSONB (`apps/user-management/src/models/policy.model.ts:8-25`, JSONB at :16, paranoid at :23). Typed row declares `rule: unknown` (`user-management.shape.ts:71-81`, rule at :76). Joi only requires `rule` to be an object with unknown keys (`apps/user-management/src/validators/admin-surface.validator.ts:10-24`).
- **One row = one policy rule, not a bundle:** `permission`, `effect`, and `priority` are row-level columns; the JSONB `rule` is the *condition payload* of that single rule (it can hold multiple ANDed conditions, not multiple independent policies).
- **PAP API** (`apps/user-management/src/controllers/policy.controller.ts:16-39`): `GET /policies` (`Permission.PolicyView`), `POST /policies` (`Permission.PolicyManage` + `createPolicySchema`), `PATCH /policies/:id`, `DELETE /policies/:id` — mounted under `/user-management` + `ApiConstants.PublicPrefix`.
- **`PolicyRepository.list` returns rows ordered `priority ASC`** (`apps/user-management/src/repositories/policy.repository.ts:9-13`, order at :11) — and returns **all** rows including `is_active=false` (no filter, no pagination).
- **No event on write:** `PolicyService.create/update/delete` are pure CRUD inside `withTenantTransaction` (`apps/user-management/src/services/policy.service.ts:19-66`) — no bus publish, no `invalidatePolicies()` call. `toDto` (`policy.service.ts:68-77`) keeps DB field names (`permission`, `rule`) and never produces `AccessShape.PolicyRule`. Note for Q5: `update` patches via the repository's `findByPk` under the RLS transaction (`policy.repository.ts:29-30`) and never captures the **pre-update** `permission` value — a permission-renaming PATCH needs it to invalidate the *old* cache key, so the service must be extended to return/capture it (Q5 step 5).

**The dormancy, precisely:** the PDP's only `PolicyRule[]` producer is the in-code `amountCapPolicies` loader reading JWT claims (`policy-loader.ts:62-75`); no code bridges `policies` rows into enforcement (`policy-loader.ts:28-29` documents the DB loader as future work). Today: **RBAC = DB-persisted Casbin (live); ABAC = one hardcoded JWT-attribute amount cap; persisted PAP policies (including their `priority` column) = write-only storage with zero enforcement effect.**

### 1.5 The hardcoded helper + RLS backstop

`amountCapPolicies(action)` (`policy-loader.ts:62-75`) synthesizes, per request, a single deny-override from the JWT claim:

```ts
const cap = readNumber(principal.attributes, APPROVAL_LIMIT_ATTR);   // 'approvalLimit', :33
if (cap === undefined) return [];                                    // zero policies ⇒ RBAC alone decides
return [{ id: `amount-cap:${action}:${cap}`, effect: 'deny', action,
          conditions: [{ attribute: 'resource.amount', operator: 'gt', value: cap }] }];
```

Wired on exactly two routes, both `Permission.ExpenseReportApprove`: `POST /reports/:id/decisions` and `POST /reports/:id/approve` (`expense-report.controller.ts:91, :119`). `combinePolicies(...loaders)` concatenates loaders (`policy-loader.ts:81-86`). The resource half **is** populated — `loadReportResource` sets `ownerId = submitter_id` and `attributes: {status: report.status, amount: Number(report.total_amount)}` (`expense-report.controller.ts:243-253`, attributes at :251) — but sets **neither `resource.teamId` nor `resource.tenantId`**. Two consequences: (a) `own_and_team` has nothing to compare against on expense (Q10); (b) the PDP's tenant-isolation step (`pdp.ts:29, :75`) **can never fire on the reference route** — it is vacuous there, and RLS is the only tenant gate on that path (annotated in §2.3; new resource loaders should set `tenantId`, Q9). One more observation for §6: the deny reason — with the approver's cap embedded in the policy id (`amount-cap:{action}:{cap}`, `policy-loader.ts:68`) — flows **verbatim to the client** in the 403 body (`pep.ts:286` passes `decision.reason` to `ErrUtils.forbidden`; 4xx messages pass the error middleware unredacted, `error.middleware.ts:46-53`), leaking the principal's approval limit today; DB-backed denials would leak policy UUIDs the same way. RLS (`libs/db/src/rls.ts:38-54`) remains the DB-level tenant backstop underneath everything.

### 1.6 The CRITICAL attribute-population gap (why §0's prerequisite is load-bearing)

`teamIds` and `approvalLimit` are **never written into any token** → `principal.attributes` is always undefined → the amount-cap and the `own_and_team` team dimension are **silent no-ops**: no error, no log, no metric flags the inert gate. Chain of evidence: `auth.service.ts:54-61` (claims without attributes) + `user.repository.ts:95-112` (`getAccess` returns only roles/permissions/scope) + `user-management.shape.ts:478-485` (`JwtClaims` has no attributes member) + `pep.ts:54-61` (principal copies the absent claim). Three more facts scope the fix:

- **There is no source of truth for `approvalLimit` at all** — no `users.approval_limit` column, no tenant config. Populating it needs a new data source, not just plumbing.
- **Team data exists but never feeds the token — and it is process-local to user-management:** `TeamMember` is an identity model defined only in `apps/user-management/src/models/team-member.model.ts` and queried only for contact listing (`user.repository.ts:80-83`); invites carry `team_ids` for membership creation (`apps/user-management/src/services/invite.service.ts:42`), not claims. A lazy PIP running inside expense/invoice/payroll therefore has the **same cross-process data-access problem as the policy read** — and gets the same solution: a shared-lib read over the shared DB (§3 Q10).
- **Non-IdP token issuers widen the surface:** `scripts/demo/agent-loop-demo.ts:111` and `scripts/mcp/aegis-mcp-stdio.ts:92` sign only `{sub, tenant_id, roles}` — no attributes, no permissions, no scope. Those principals skip row scope entirely (`scope == null ⇒ ok`, `scope.ts:19-21`) and take the `evaluateAbac` path. The PIP design must cover them (lazy PIP does; issue-time claims alone do not).
- **`users.tenant_id` sits directly on the users row** (`apps/user-management/src/models/user.model.ts:13`, `allowNull: false`) — one user row per tenant, no memberships table — so *per-tenant* attributes (a per-tenant approvalLimit, per-tenant team sets for one identity) have no natural home yet (§4 note 3).

> **Correction to a common premise:** `AccessShape.PolicyRule` has **no** `priority` field (`access.shape.ts:59-66`) and the PDP never sorts. `priority` lives only on the DB row and is used solely for list ordering (`policy.repository.ts:11`). Deny-overrides is order-independent by construction. §3 Q8 defines how to handle priority anyway.

### 1.7 Reference comparison — oe_core (what to borrow, what to avoid)

oe_core (`/Users/ankurpandey/Documents/GitHub/oe_core`) was audited read-only as the prior-art system. Its authorization is two disjoint, non-generic layers:

| Aspect | oe_core | Aegis |
|---|---|---|
| Enforcer lifecycle | **New Casbin enforcer + new PG adapter connection + full `loadPolicy()` on every request** (`apps/backend/src/app/library/RBAC.ts:24-45, 71-72, 133-138`) | Cached process-wide enforcer + mutex + Redis reload watcher (`pep.ts:73-148`) |
| Tenancy in authz | Domain hard-coded `'*'` ("Domain is global for initial implementation", `RBAC.ts:73-74`) — none | `dom = tenantId` in Casbin + Postgres RLS (`enforcer.ts:21-36`; `libs/db/src/rls.ts:38-54`) |
| ABAC | **None.** Matcher is exact-string RBAC only (`apps/backend/src/assets/casbin/model.conf:11-14`); attribute/record decisions are hand-written SQL | Generic condition evaluator, 11 operators, dotted paths (`condition-evaluator.ts:36-76`) |
| Row visibility | 3-value per-user enum `AllJobs/PublicAndTeams/OnlyTeams` (`libs/shared/enums/src/user-access.enum.ts:1-5`) resolved by an implicit middleware fallback chain (`RBAC.ts:96-121`), enforced by SQL fragments **copy-pasted across 5+ query sites** (`libs/services/backend/src/job/job-access-queries.ts:110-227` et al.), with raw string interpolation of ids in raw-query mode (`job-access-queries.ts:89-101`) | `checkRowScope` + RLS; list predicates per service (one today) |
| Policy management | Imperative one-off migrations that open a live enforcer and add rows driven by **ordinal boolean matrices** (position = role) (`seeders/0034_side_status_item_permissions.ts:13-18, 84-96`; dozens more) | Seeded catalog + live `applyPolicyGrant` + PAP CRUD |

**Net delta:** oe_core offers nothing architecturally that Aegis lacks. Worth borrowing as *concepts*: (a) the 3-level record-visibility enum as a user-legible product abstraction — expressible in Aegis as canned policy/scope templates, not a bespoke column; (b) the `job_reviewers` escape hatch (reviewer/approver access beyond team scope, `job-access-queries.ts:159-191`) — should become a policy condition, not a SQL OR-clause; (c) a display-name permission catalog table for admin UI (`seeders/0034:20-24, 73`); (d) explicit deny semantics — which Aegis's PDP already has (`pdp.ts:34-38`). Its mechanics (per-request enforcer construction, `'*'`-only domains, ordinal seed matrices, duplicated access SQL, internal calls hardcoding `AllJobs` — `InternalApiAdapter.ts:32`) are anti-patterns this design explicitly avoids (§7).

## 2. Recommended target architecture

**Goal:** a generic, cached, fail-closed DB-backed policy loader that converts persisted `policies` rows into `AccessShape.PolicyRule[]`, plus a PIP that populates `principal.attributes` — both consumable from **every service process** (§1.1 topology) with no application service importing user-management internals.

### 2.1 Components

| Component | Responsibility | Home (rationale in §3 Q7) |
|---|---|---|
| **Row→PolicyRule mapper** | Pure function `PolicyRow → PolicyRule \| MappingError`: filters `is_active`, validates `permission` against the `Permission` enum (or `'*'`), parses/validates `rule` JSONB into `conditions[]` (rejecting `scope` — dead in the runtime, §1.2), resolves nothing itself. Contract: **all-or-nothing per (tenant, action)** — any `MappingError` fails the whole load (Q1/Q8) | `libs/access-control` |
| **DB-backed policy loader** | `dbPolicies(action): PolicyLoader` — fetches tenant+permission rows through the versioned cache, maps them, applies per-request `$attr` interpolation (Q3), returns `PolicyRule[]`; same signature as `amountCapPolicies` (`policy-loader.ts:39-42`) so `combinePolicies` (`:81-86`) composes them | `libs/access-control` |
| **Policy read port** | Interface `PolicyReadPort { listActive(tenantId, permission): Promise<PolicyRow[]> }` + a **default shared-DB implementation** (raw parameterized SELECT via `withTenantTransaction`, the `feature-flags-reader.ts` pattern) registered in **each consuming service's bootstrap** — user-management is *not* the only process that needs it (§2.2, Q6) | interface + default impl in `libs/access-control` (impl depends on `@aegis/db` only) |
| **Policy cache** | Shared Redis, **versioned keys**: `abac:polver:{tenantId}:{permission}` (monotonic version) + `abac:pol:{tenantId}:{permission}:v{n}` (mapped rules, TTL). No per-pod L1 and no pub/sub in v1 (Q4/Q5) | `libs/access-control` |
| **PIP** | Interface `AttributeReadPort { load(tenantId, userId): Promise<Record<string, unknown>> }` + default shared-DB implementation (reads `team_members`, later the approval-limit source); invoked by an explicit hook in `authorizeAny` after Gate 1, before the `policies:`/`resource:` loaders run (Q10); per-(tenant,user) cache with a documented TTL revocation bound | interface + default impl in `libs/access-control`; registered per-service at bootstrap |
| **Invalidation** | `PolicyService` writes: after the tenant transaction commits, `INCR` the version key(s) — old **and** new permission on a rename (requires capturing the pre-update permission, §1.4/Q5). No pub/sub channel needed while the cache is shared-Redis-only; a dedicated ABAC channel is introduced **only if** a per-pod L1 is added later (Q5) | `apps/user-management` (write path) + `libs/access-control` (key helpers) |

### 2.2 How `authorize()` consumes it in a multi-process deployment

**The constraint first (this is what the naive design got wrong):** Aegis is a gateway + separate service processes (§1.1). Registering a concrete `PolicyReadPort` "at user-management bootstrap" would put it **only in the user-management process**; every `dbPolicies`-wired route in expense/invoice/payroll would find the port unregistered, and — under the fail-closed boot-order guard (Q6) — deny 100% of requests. The wiring below is therefore *per consuming service*, riding the two patterns the repo already sanctions: shared-lib reads over the one shared Postgres (`getApprovalContext()`, `apps/expense/src/bootstrap.ts:31-32`) and model-free raw SELECTs under RLS (`feature-flags-reader.ts:19-29`).

Routes keep the existing one-liner shape; only the loader changes:

```ts
// apps/expense/src/bootstrap.ts — one new line beside getApprovalContext():
registerAccessControlPorts(); // installs the shared-DB PolicyReadPort + AttributeReadPort (libs/access-control)

// route (unchanged shape):
authorize(Permission.ExpenseReportApprove, {
  resource: (req) => loadReportResource(req),
  policies: combinePolicies(
    dbPolicies(Permission.ExpenseReportApprove),        // NEW: persisted rows via port + versioned cache
    amountCapPolicies(Permission.ExpenseReportApprove), // legacy leg, kept until parity (§5 Phase 5)
  ),
})
```

- `dbPolicies` lives in `libs/access-control` and depends on the injected `PolicyReadPort` **interface**, never on `PolicyService`/the user-management `Policy` model. The **default implementation also ships in `libs/access-control`**: a raw, parameterized `SELECT ... FROM policies WHERE permission IN ($1,'*') AND is_active = true` inside `withTenantTransaction` (`libs/db/src/transaction.ts:10-20`) — RLS-scoped, Sequelize-model-free, exactly the `featureFlagReader` shape. This adds one clean dependency edge (`libs/access-control → @aegis/db`, for transaction plumbing only); the zero-new-edge alternative is a minimal read-only model registry in a tiny shared lib à la `libs/approvals/src/models/database-context.ts` (Q6 weighs both).
- **Every service that wires `dbPolicies` (or the PIP) calls `registerAccessControlPorts()` in its own bootstrap** — expense, invoice, payroll, and user-management alike. Miss the registration and the boot-order guard makes the loader **throw ⇒ request blocked (5xx)** on first use (Q6), plus a loud boot-time error log; the §6 test matrix pins this.
- Controllers still import only `@aegis/access-control` — identical ergonomics to importing `amountCapPolicies` today (`expense-report.controller.ts:91`). Nothing ever imports `PolicyService`, the user-management `Policy` model, or another app's Sequelize context.
- **PEP change honesty:** the PEP is untouched in Phases 0–1 (`authorize()` already accepts any async `policies:` loader, `pep.ts:207-211, 274`). Phase 2 adds **one deliberate PEP hook** — the PIP attribute-resolver invoked inside `authorizeAny` (Q10) — and Phase 4 adds `environment` to the PDP request. Neither is "free"; both are scoped, tested changes.
- Rejected alternative: an HTTP fetch from user-management's PAP (`GET /policies`) with the Redis cache in front. It adds a synchronous availability dependency of every authorize() on the user-management service, an extra network hop on cache miss, and auth for the internal call — for no isolation gain while both sides share one Postgres. Revisit only if the database ever splits per service.

## 3. Answers to the specific questions

### 1. How to convert rows in `policies.rule` into `AccessShape.PolicyRule[]`

One row = one rule (single `permission`/`effect`/`priority` per row; §1.4). Map field-by-field with a **pure** mapper in `libs/access-control` returning `PolicyRule | MappingError` per row — and an **all-or-nothing loader contract**: if *any* row fetched for a (tenant, action) maps to `MappingError`, the whole load **fails for that action ⇒ the request is blocked ⇒ alert**. This applies to **both effects**: a silently dropped deny fails open directly, and a silently dropped *allow* fails open too, by emptying the allow-gate (`pdp.ts:47-50, 93-97`; §1.2). Never partially filter.

| `PolicyRow` (DB, `user-management.shape.ts:71-81`) | `AccessShape.PolicyRule` (`access.shape.ts:59-66`) | Notes |
|---|---|---|
| `id` | `id` | direct — surfaces in deny reasons (`denied by policy ${id}`, `pdp.ts:36`); see the reason-hygiene note below |
| `tenant_id` | `tenantId` | direct |
| `effect` | `effect` | same `'allow'\|'deny'` union; DB CHECK-constrained (`0028:45-50`) |
| `permission` (free string) | `action: Permission \| '*'` | **rename + validate**: must be a known `Permission` value or `'*'`; unknown ⇒ `MappingError` ⇒ failed load. (`'*'` *allow* rows are additionally banned — at write time; a legacy one encountered at load is also a `MappingError`, never a silent skip. §3 Q8) |
| `rule` (JSONB, `unknown`) | `conditions?: PolicyCondition[]` | **parse + validate** — see envelope below. **A `scope` key ⇒ `MappingError`:** `PolicyRule.scope` is consumed by nothing in the runtime (`pdp.*` never reads it; `checkRowScope` reads only `principal.scope`, `scope.ts:18`) — accepting it would ship a write-accepted, never-read field, recreating §1.6's administered-but-inert failure class. v2 may add PDP support (e.g. strictest-scope-among-matched-rules applied to the resource) as a deliberate, tested change; until then reject at PAP write time *and* at map time |
| `is_active` | — | filter: drop rows where `is_active !== true` (repository `list()` does NOT filter; `policy.repository.ts:9-13`) — this is the one *legitimate* row drop, since inactive is an administered state, not a parse failure |
| `deleted_at` | — | paranoid model already excludes soft-deleted rows (`policy.model.ts:23`) |
| `priority` | — | not on `PolicyRule`; used only to sort loader output for determinism (Q8) |

**Canonical `rule` envelope** (a convention to define and validate — nothing enforces one today; `rule` is `unknown` end-to-end, Joi checks only "is an object", `admin-surface.validator.ts:13,21`). v1 envelope = **`conditions` only** (no `scope`, per above):

```json
{
  "conditions": [
    { "attribute": "resource.amount", "operator": "gt", "value": 50000 },
    { "attribute": "resource.amount", "operator": "gt", "value": { "$attr": "principal.approvalLimit" } }
  ]
}
```

Mapper validation rules: each condition must have a string `attribute` whose root is one of `principal|resource|environment|action`, an `operator` from the 11-operator whitelist (`condition-evaluator.ts:39-66`), and a present `value` (except `owner`/`tenant_match`, which ignore it). A `value` may be a literal **or** an `$attr` reference (resolved per request by the loader — Q3); `$attr` paths are validated against the same root whitelist. **Reject-on-parse-failure — never coerce a malformed rule into `conditions: []`**, because empty conditions are vacuously true (`condition-evaluator.ts:70-76`): a garbled allow would always match, and a garbled deny would deny everything for that action. Distinguish deliberately: an *explicit* `{"conditions": []}` on a deny row means "unconditional deny for this action" (legitimate); an unparseable blob means `MappingError` ⇒ failed load ⇒ alert. Since `rule` defaults to `{}` (`0028:35`), decide and document whether `{}` means unconditional (recommended: treat `{}` as `conditions: []`, i.e. unconditional, since the DB default makes it common — but log a warning for unconditional *deny* rows).

**Reason hygiene:** `id` flows into `denied by policy ${id}` which reaches the client verbatim today (§1.5). When generalizing, return a **generic client message** ("denied by policy") and log the policy id + full reason server-side, correlated — otherwise every DB deny leaks policy UUIDs (and the legacy helper already leaks the approver's cap through its synthetic id, `policy-loader.ts:68`). §6 has the test.

### 2. Whether the current `policies` table shape is sufficient or needs schema changes

**Sufficient for v1 — no migration required.** Columns cover effect, action (`permission`), conditions (`rule` JSONB), priority, tenant (FK + RLS), is_active, soft delete, audit columns; both needed indexes exist (`0028:43-44`). Required hardening (validator + one-time audit, not schema):

- **Write-time validation:** extend `createPolicySchema`/`updatePolicySchema` (`admin-surface.validator.ts:10-24`) to validate the full Q1 envelope: `permission` against the `Permission` enum (today it is any ≥3-char string, so unmappable rows can be persisted), operator whitelist, `$attr` path whitelist, **reject `scope`**, **reject wildcard-action `allow`** (Q8). Rejecting at the PAP beats rejecting at load — under the all-or-nothing load contract, one bad persisted row blocks the whole action until fixed.
- **One-time data audit/migration:** scan existing `policies` rows for envelope violations (wildcard allows, `scope` keys, unknown permissions, malformed `rule`) *before* Phase 1 wires any route — the write-time validator only protects new writes; pre-existing rows must be fixed or deactivated by hand, **never** silently filtered at load (that is exactly the fail-open the contract forbids).
- **Later, if needed:** a `resource_type` column if policies should scope to a resource kind rather than a bare permission (v1 can encode this as a condition); promote `scope` to a column **if and when** the PDP learns to consume it (Q1); pagination on `PolicyService.list()` (currently returns every row including inactive, `policy.service.ts` / `policy.repository.ts:9-13`).
- **Naming caution:** three unrelated `PolicyRow` types exist (`UserManagementShape.PolicyRow`, `ApprovalShape.PolicyRow`, `ReportingShape.ReportAccessPolicyRow`) plus two `policy.repository.ts` files (user-management and `libs/approvals`). Do not "unify" them — they are different concepts (§4 note 6, §7).

### 3. How to support dynamic values like `principal.approvalLimit`, `resource.amount`, `resource.status`, `environment.time`

Two distinct kinds of "dynamic" — the doc previously conflated them:

**(a) Dynamic LEFT side (attribute paths).** The evaluator already resolves all four roots by dotted path with transparent `attributes`-bag fall-through (`condition-evaluator.ts:4-29`, :26) — a persisted policy just uses the path string. What varies is **who populates the value**:

| Dynamic value | Condition `attribute` | Populated by | Status today |
|---|---|---|---|
| `principal.approvalLimit` | `principal.approvalLimit` | **PIP** (Q10, §5 Phase 2) — plus a **new source of truth** (no `users.approval_limit` column exists anywhere) | **Never populated** (`auth.service.ts:54-61`) — this is the silent no-op |
| `resource.amount` | `resource.amount` | route resource loader | Already set: `attributes.amount = Number(report.total_amount)` (`expense-report.controller.ts:251`) |
| `resource.status` | `resource.status` | route resource loader | **Already set on expense**: `attributes: {status: report.status, ...}` (`expense-report.controller.ts:251`) — earlier drafts wrongly claimed otherwise. Invoice/payroll have **no resource loaders at all** yet (Q9) |
| `environment.time` | `environment.time` | **PEP** — `authorize()` must build the request with `environment: { time: Date.now(), ip: req.ip }` | **Never populated**: `pep.ts:283-284` passes only `{principal, action, resource}`, so `environment.*` silently resolves undefined. Small additive PEP change (§5 Phase 4) |

**(b) Dynamic RIGHT side (attribute-to-attribute comparison) — a real capability gap.** The evaluator compares `cond.value` as a **literal** (`asNumber(value)`, `condition-evaluator.ts:44-51`); there is no operator that compares two attributes, so **no persisted row can express `resource.amount > principal.approvalLimit`** — the per-approver amount cap, the flagship use case. `amountCapPolicies` only works by synthesizing the rule per request with the cap baked into `value`. The fix is an **attribute-reference value convention**: `value: {"$attr": "principal.approvalLimit"}` (optionally `{"$attr": {"path": ..., "missing": "skip"|"fail"}}`), with two implementation options:

1. **Loader-side interpolation (recommended — zero PDP/evaluator change):** `dbPolicies` already receives `(principal, resource)` per the `PolicyLoader` signature (`policy-loader.ts:39-42`). The cache stores the raw mapped rules with `$attr` markers intact; after every cache read the loader substitutes each `$attr` ref from the live request **per request**. Fail-closed default: an unresolvable ref (attribute absent) ⇒ treat as a failed load for that action ⇒ blocked + alert. The explicit `missing: "skip"` knob drops *that rule* instead — which is exactly the legacy helper's "no cap ⇒ no policy ⇒ RBAC decides" semantics (`policy-loader.ts:64-65`), so the amount-cap migration rule uses it to preserve parity for unconfigured approvers. Which of the two an org wants for amount caps is a **product sign-off**, not a default.
2. **Evaluator-side resolution:** teach `evalCondition` to resolve `$attr` values via `resolveAttr` before comparing, fail-closed on unresolvable refs. More general (works for any loader, including future ones), but it is a PDP-adjacent change and v1's mantra is "no evaluator changes"; defer to v2 unless a second loader needs it.

**This capability gates §5 Phase 5:** without it, no persisted row can replicate `amountCapPolicies`, "parity" is unachievable by construction, and retiring the helper would silently regress per-approver caps. Q9's Phase-2 parity harness is specified accordingly (multiple (limit, amount) pairs — a fixed-threshold rule that happens to pass at one amount proves nothing).

No new *operators* are needed for expense-first (`gt` covers amount caps; `gte`/`lte` on `environment.time` cover time windows once the PEP passes environment). Number-coercion caveat: `lt/lte/gt/gte` coerce with `Number(...)` (`condition-evaluator.ts:39-66`), so a missing/garbage left side becomes `NaN` and every comparison is false — for a *deny* rule that means "does not deny" (§6, number-coercion row).

### 4. How to cache DB-backed policies safely (Redis, tenant+permission scoped)

- **Topology (settled — earlier drafts hand-waved this):** **shared Redis only (one logical L2), no per-pod in-memory L1, no pub/sub** in v1. With a single shared cache, invalidation is a writer-side operation on shared keys and every pod sees it on its next read; pub/sub fan-out would be redundant (N pods DELing the same shared key). An L1 + dedicated invalidation channel is a deliberate later optimization (Q5).
- **Keys — versioned (this is the "version stamp", now with an actual protocol):**
  - `abac:polver:{tenantId}:{permission}` — a monotonic integer version, `INCR`ed by the writer **after commit** (Q5). Missing ⇒ reader initializes to 1 (`SET NX`).
  - `abac:pol:{tenantId}:{permission}:v{n}` — the *mapped, is_active-filtered, priority-sorted* `PolicyRule[]` for version `n` (post-map so the hot path never re-parses JSONB; `$attr` markers kept raw — interpolation is per-request, Q3). Companion `abac:pol:{tenantId}:*:v{m}` bucket for `permission='*'` rows with its own version key, because the PDP matches deny rules on `action==='*'` (`pdp.ts:34`).
  - **Reader:** GET version `n` → GET `...:v{n}` → hit ⇒ done; miss ⇒ DB read via the port → SET `...:v{n}` with TTL. **Writer:** commit → INCR version (old *and* new permission keys on a rename, Q5).
  - **Why versioning is load-bearing:** the plain cache-aside scheme has a classic race — a reader that queried the DB *just before* the writer's commit can SET the stale list *after* the writer's bust, leaving staleness until TTL **even when invalidation is delivered**. With the version in the key, that raced SET lands on `...:v{n}` while every post-INCR reader consults `...:v{n+1}` — the stale write is never read again; orphaned old-version keys just expire via TTL.
- **Honest convergence bounds (state these in the runbook, get sign-off):** a created/retired policy takes effect for **every request whose loader starts after the post-commit INCR** — sub-second in practice, no pub/sub needed. Requests already past their version GET finish on the old snapshot (in-flight only; unavoidable). If the INCR itself fails (Redis unavailable *at write time*): log + alert on the write path, and convergence degrades to the TTL (30–60s) — during which a *new deny* (e.g. a fraud-response cap) may under-enforce for up to TTL; that residual window is the thing to sign off, not to paper over. (Readers facing the same Redis outage fall through to direct DB reads, which are fresh — the degraded window only exists for the partition asymmetries in between.)
- **TTL:** short (30–60s) on the value keys — the safety net for lost INCRs and the GC for orphaned versions; never the primary consistency mechanism.
- **Tenant isolation:** the tenant segment of the key is mandatory; never a cross-tenant key. The DB read behind a miss runs in an RLS-scoped transaction, so even a mis-scoped key cannot fetch another tenant's rows — RLS is the backstop, the key is the contract.
- **Negative caching:** cache the empty result (tenant with no policies for a permission) at the current version with the same TTL, or every request on quiet tenants pays a query.
- **Failure ladder (fail-closed, with honest status codes):** Redis error ⇒ fall through to a direct DB read (correct, slower); DB error ⇒ **throw a typed system error** (`POLICY_LOAD_FAILED`) — the request is blocked. Do not return `[]` (for allow-gated actions an empty list vacuously passes the gate, `pdp.ts:47-50` — an outage would become an authorization bypass). Per §1.1, the throw surfaces as **5xx with a generic client message** (`pep.ts:294-296` → `error.middleware.ts:31-33, :53`), not 403 — deliberate: 403 = denied by policy, 5xx = could not evaluate. This mirrors the enforcer's posture (`enforcer.ts:103-114`; `pep.ts:124-148`) while keeping ops triage honest; §6 tests assert "blocked with 5xx", not "403".

### 5. How to invalidate the policy cache when the PAP changes policies

Today: **nothing fires on ABAC policy writes.** `PolicyService` is pure CRUD (`policy.service.ts:19-66`). The existing Redis channel `POLICY_RELOAD_CHANNEL = 'aegis:access-control:policy-reload'` (`watcher.ts:30`) is published only by Casbin RBAC grant projection (`applyPolicyGrant`, `pep.ts:188-202`) and means "reload the Casbin enforcer."

Plan — **version-key INCR, not pub/sub** (see Q4 for why pub/sub is redundant against a shared-Redis-only cache, and §1.1 for why the current watcher couldn't carry it anyway):

1. In `PolicyService.create/update/delete`, **after the tenant transaction commits**, `INCR abac:polver:{tenantId}:{permission}` (and the `*` bucket's version when the row's permission is `'*'`). Synchronous on the write path; on Redis failure log + alert (`ABAC_INVALIDATION_FAILED`) — convergence then falls to the TTL bound (Q4).
2. Invalidate on **every** transition that changes effective policy: create, condition/effect/priority PATCH, `is_active` flips both ways, and DELETE/soft-delete.
3. If a PATCH changes the `permission` value itself, INCR **both** old and new version keys. **Service change required:** the update path patches via `findByPk` under the RLS transaction (`policy.repository.ts:29-30`) and never captures the pre-update permission — the repository already holds the old row in hand, so return it (or its `permission`) to the service alongside the patched row, and INCR both keys post-commit.
4. **Convergence contract (replaces the earlier overstated "one publish round-trip"):** a retired/changed policy stops/starts enforcing for every request whose loader runs after the INCR; the raced-SET staleness mode is structurally eliminated by the versioned keys (Q4); TTL is the bound only when the INCR itself is lost, and that residual under-enforcement window needs explicit sign-off.
5. **Pub/sub is deferred, not banned:** if a per-pod L1 cache is ever added, introduce a **dedicated channel** (e.g. `aegis:access-control:abac-policy-reload`) carrying `{tenantId, permission, version}` — do **not** reuse `POLICY_RELOAD_CHANNEL` (it means "reload the Casbin enforcer"; sole publisher `pep.ts:201`). Size the watcher rework honestly at that point: `watcher.ts` is single-channel with a single handler that ignores the payload (`:65-66`, bare timestamp published at `:100`) and is fail-open at startup **with no retry** — a pod booting during a Redis outage never subscribes even after Redis recovers (`:74-81`; nothing re-calls `startPolicyWatcher`). Multi-channel dispatch, payload parsing, and reconnect/retry are all new work, which is one more reason v1 avoids depending on it.

### 6. How to wire generic policy loading into `authorize()` WITHOUT every service importing user-management internals

**First, name the actual difficulty:** "don't import user-management internals" is easy *within one process*; Aegis runs as a gateway + separate service processes (§1.1), so the real problem is that `dbPolicies` executes inside **expense/invoice/payroll processes** where no user-management code runs at all. Pure dependency inversion with the implementation registered "in user-management" solves the import problem and fails the deployment one — the port would be unregistered everywhere it is actually needed, and the fail-closed guard would turn that into a 100% outage of the wired routes. The design therefore splits interface and *deployment* of the implementation:

- `libs/access-control` defines `PolicyReadPort` (interface) and `dbPolicies(action)`, which returns a `PolicyLoader` — the exact signature `authorize()` already consumes (`pep.ts:207-211, 274`) and `amountCapPolicies` already implements (loaders may be async; the PEP awaits them).
- **The default port implementation is shared, not app-owned** — pick one of the repo's two sanctioned shared-read patterns (recommend (a)):
  - **(a) Model-free raw SELECT in `libs/access-control`** (the `featureFlagReader` pattern, `libs/db/src/feature-flags-reader.ts:19-29`): a parameterized `SELECT id, tenant_id, permission, effect, rule, priority, is_active FROM policies WHERE permission IN ($1, '*') AND is_active = true` inside `withTenantTransaction` (`libs/db/src/transaction.ts:10-20`). RLS applies (FORCE + RESTRICTIVE, `0028:111-117`). Adds one dependency edge `libs/access-control → @aegis/db` (transaction plumbing only — no policy semantics move into `libs/db`, Q7).
  - **(b) Minimal read-only model registry in a shared lib** à la `libs/approvals/src/models/database-context.ts:31-48` (which expense already boots at `bootstrap.ts:31-32`): a `getPolicyReadContext()` defining just a read-only `Policy` model on the shared connection. Keeps `libs/access-control` dependency-free (the registry lives beside it) at the cost of a Sequelize model definition duplicated from user-management's.
- **Per-service bootstrap step (explicit, one line, every consumer):** `registerAccessControlPorts()` in `apps/expense/src/bootstrap.ts` (beside `getApprovalContext()`, :31-32), `apps/invoice/src/bootstrap.ts`, `apps/payroll/src/bootstrap.ts`, and `apps/user-management/src/bootstrap.ts` (which already initializes shared infra there — event bus at :19, policy watcher at :23). - Controllers in `apps/expense`/invoice/payroll import **only** `@aegis/access-control` — identical to how they import `amountCapPolicies` today (`expense-report.controller.ts:91`). Nothing ever imports `PolicyService`, the user-management `Policy` model, or Sequelize models from another app.
- `combinePolicies(dbPolicies(a), amountCapPolicies(a))` (`policy-loader.ts:81-86`) runs both legs during the parity window (§5 Phase 5, §7).
- Boot-order guard: if a route uses `dbPolicies` before the port is registered, the loader **throws** (⇒ request blocked, surfacing as 5xx per Q4) — never returns `[]` — and the service logs a loud boot-time error when a known-consumer bootstrap skips registration. §6 pins both.
- Rejected: HTTP fetch from the user-management PAP (§2.2 — availability coupling + extra hop for zero isolation gain while the DB is shared; the documented fallback if the database ever splits per service).

### 7. Whether this belongs in `libs/access-control`, `libs/db`, or a new shared policy client

**Primary home: `libs/access-control`.** It already owns the PDP, condition evaluator, scope, the `PolicyLoader` type, `amountCapPolicies`, the enforcer, and the watcher — the mapper, `dbPolicies`, both port interfaces, the versioned-cache client, **and (option (a)) the default shared-DB port implementations** belong beside them.

- **Not `libs/db`:** it owns RLS/transaction plumbing (`libs/db/src/rls.ts`) and must stay ignorant of `PolicyRule` semantics. Note the direction: `libs/access-control` *depending on* `@aegis/db` for `withTenantTransaction` (option (a), Q6) is fine and precedented (`feature-flags-reader.ts` shows the exact raw-read shape); policy semantics migrating *into* `libs/db` is what's forbidden.
- **Not a new shared policy client package:** unnecessary surface today — unless option (b) (read-only model registry) is chosen, in which case that registry is a deliberately tiny new lib mirroring `libs/approvals`' database-context and nothing more. Extract a fuller standalone client only if a *second* consumer outside access-control ever needs raw policy rows (none exists).
- **The concrete DB read is deliberately NOT in `apps/user-management`** (a correction to the naive design): user-management remains the *write* owner (PAP CRUD + invalidation INCRs), but the *read* must execute inside every consuming process (§1.1, Q6) — so it lives in shared code, RLS-scoped, and is registered per-service at bootstrap.

### 8. How to preserve deny-overrides and priority ordering

- **Deny-overrides is already guaranteed and order-independent:** the PDP scans *all* policies and any matching deny wins before allow-gating is even consulted (`pdp.ts:34-38, 80-84`). The loader cannot break this by ordering; it *can* break it by dropping rows — and the failure is symmetric: a silently dropped **deny** fails open directly, and a silently dropped **allow** fails open by emptying the allow-gate (`pdp.ts:47-50, 93-97`; §1.2). Hence the Q1 contract: **any unmappable or policy-violating row, either effect, fails the whole load for that action ⇒ request blocked ⇒ alert.** "Reject the bad row and keep going" is not a safe mode for either effect.
- **Priority is not consumed by the PDP today** (`PolicyRule` has no `priority`, `access.shape.ts:59-66`; no sort in `pdp.ts`). Two options:
  1. **v1 (recommended):** keep PDP semantics exactly as-is; sort loader output `priority ASC, id ASC` (the repository already orders `priority ASC`, `policy.repository.ts:11`) purely for **determinism** — stable deny-reason selection when several denies match, and stable obligation selection once obligations flow. Document in the PAP admin surface that priority is ordering/tie-break only: deny already dominates allow at any priority.
  2. **v2 (only if a real requirement emerges, e.g. "this allow exempts that deny"):** first-match-by-priority semantics. That is a **PDP behavior change** — add `priority?` to `PolicyRule`, sort, first matching rule wins. Gate it, test it exhaustively, and do not do it opportunistically; deny-overrides is the safer default and matches all current code and tests.
- **Wildcard caveat:** because of the `decide` vs `evaluateAbac` divergence on `'*'` *allow* rules (`pdp.ts:47` vs `:93`), wildcard-action **allow** policies are banned in v1 — **enforced at PAP write time** (Q2 validator) plus the one-time audit of already-persisted rows; a legacy wildcard-allow encountered at load is a `MappingError` (failed load, alert), **never a silent filter** — silent filtering is precisely the dropped-allow fail-open above. Wildcard **deny** is consistent on both paths (`pdp.ts:34, 80`) and fine.
- **Retirement dependency (cross-ref):** preserving the *helper's* deny behavior through migration additionally requires the Q3 cross-attribute capability — a literal-value deny cannot express the per-approver cap, so deny-parity for `amountCapPolicies` is not just a loader-correctness question (§5 Phase 5).

### 9. How to test this with expense approval first, then invoice/payroll sensitive routes

**Expense approval is the reference route** because everything is already staged there: the two guarded endpoints (`expense-report.controller.ts:91, :119`), a resource loader that populates `resource.amount`, `resource.status`, and `ownerId` (:243-253, attributes at :251), and the legacy loader to prove parity against. **Invoice and payroll are NOT similarly staged:** neither app has any resource loader, `ResourceRef` usage, or `policies:` option anywhere in its controllers (verified by search) — their steps below build that from scratch.

1. **Phase 1 test (no PIP needed):** persist a tenant policy `{permission: 'expense-report:approve', effect: 'deny', rule: {conditions: [{attribute: 'resource.amount', operator: 'gt', value: 50000}]}}`. Assert (a) under-cap approve ⇒ allow; (b) over-cap approve ⇒ 403 with a **generic** deny message (policy id in the server log only — Q1 reason hygiene); (c) tenant B's identical action unaffected (RLS + key isolation); (d) `is_active=false` ⇒ not enforced; (e) DELETE ⇒ stops enforcing per the Q4/Q5 convergence contract (next-request after INCR; TTL if INCR lost). This exercises loader+mapper+cache+PDP **using only resource attributes with literal values** — deliberately independent of both the PIP and the `$attr` capability.
2. **Phase 2+ parity test (PIP + `$attr` live):** persist the *general* cap rule `{effect:'deny', rule:{conditions:[{attribute:'resource.amount', operator:'gt', value:{"$attr": {"path": "principal.approvalLimit", "missing": "skip"}}}]}}`. **Parity harness — a matrix, not a point check:** run helper-only vs DB-only vs both (`combinePolicies`) across multiple `(approvalLimit, amount)` pairs — cap < amount, cap > amount, cap = amount, **no cap at all** (must reproduce the helper's "unconfigured approver passes on RBAC" semantics via `missing: skip`), and garbage/absent `amount` (NaN row of §6) — asserting identical outcomes cell-by-cell. A single fixed-threshold rule passing at one amount is exactly the false-parity trap this harness exists to prevent (the earlier draft's single-value test would have "proven" parity while diverging everywhere else).
3. **Invoice approve (loader built from scratch):** write `loadInvoiceResource` (~15 lines modeled on `loadReportResource`, `expense-report.controller.ts:243-253`) setting `type`, `id`, `ownerId`, **`tenantId`** (so the PDP tenant-iso layer is live, unlike expense today — §1.5), and `attributes: {status, amount}`; add `registerAccessControlPorts()` to invoice's bootstrap; wire `dbPolicies(Permission.InvoiceApprove)`; policy `deny when resource.status eq 'draft'` plus an amount deny. Proves a second resource shape with zero library changes — but it is a *new loader + bootstrap wiring*, not a one-line tweak.
4. **Payroll sensitive read (loader + allow-gating + rollout caveats):** same from-scratch loader work; an *allow* policy gating the read (allow-gating path, `pdp.ts:47-50/93-97`) plus a `mask_columns` obligation. **Three cautions:** (a) obligations require the PDP change first — `decide()`/`evaluateAbac()` never return obligations today (`pdp.ts:53, 94, 99`; §1.2); (b) this route is RBAC-only today, so wiring `policies:`/`resource:` **activates Gate 2**, and permissions-carrying principals whose JWT predates a runtime Casbin grant will 403 on `decide()` step 1 (`pdp.ts:24`) until re-login — schedule the wiring against token TTL and warn in the rollout notes (§1.2, §6); (c) losing the allow row must fail the load, not open the gate (Q8) — test it here specifically.
5. Each adoption = one resource-loader function + route wiring + the one-line bootstrap port registration (Q6) + policy rows — independently shippable.

### 10. Gaps around row scope, especially `own_and_team`

- **`own_and_team` requires `principal.attributes.teamIds`** (`scope.ts:32`) — always empty today, so the team clause never matches and the scope silently degrades to owner-only (§1.6). **The PIP must populate `teamIds`.** Same PIP that unblocks the amount cap — one prerequisite, two payoffs.
- **The lazy PIP, fully specified (previously hand-waved):**
  - **Hook point (a deliberate PEP change, §5 Phase 2 — "the PEP is untouched" holds only for Phases 0-1):** inside `authorizeAny`, after Gate 1 passes and **before** the `resource:`/`policies:` loaders run (`pep.ts:272-274`), gated on the route having those options at all. That placement is correct *and* minimal: `principal.attributes` is consumed only inside the PDP — condition evaluation and `checkRowScope` both run within `decide`/`evaluateAbac` (`pdp.ts:41, :87`) — but the `policies:` loader itself needs attributes too once `$attr` interpolation lands (Q3), so the hook must precede `opts.policies(principal, resource)` (`pep.ts:274`), not just the PDP call. RBAC-only routes never pay the fetch.
  - **Mechanism:** `AttributeReadPort { load(tenantId, userId): Promise<Record<string, unknown>> }` — interface + default implementation in `libs/access-control`, registered per-service by the same `registerAccessControlPorts()` bootstrap call as the policy port (Q6). The default impl reads `team_members` (and the approval-limit source once it exists) via the shared-DB pattern — `TeamMember` is process-local to user-management (`apps/user-management/src/models/team-member.model.ts`), so this is the identical cross-process problem and identical solution as the policy read (§1.6): raw parameterized SELECT under `withTenantTransaction`, one batched fetch per principal. The hook merges results into `principal.attributes` with **DB values overriding token claims** (revocation-correct; claims are the fallback for attributes the port doesn't own).
  - **Freshness — the revocation bound, stated honestly:** the PIP result is cached per `(tenant, user)` (`abac:attr:{tenant}:{user}`, TTL 30–60s). **v1 contract: the TTL IS the team-revocation bound** — a user removed from a team retains `own_and_team` access for up to the TTL; document it and get sign-off (the earlier "fresh on team changes" claim was wrong — a TTL cache with no invalidation is not fresh on writes). Tightening to next-request: reuse the Q4 versioned-key pattern — team-membership CRUD in user-management INCRs `abac:attrver:{tenant}:{user}` post-commit; ship it in Phase 2 if the membership write surface (invite/team services) is tractable, else as fast-follow. `approvalLimit` freshness rides the same cache and the same bound.
  - Lazy PIP covers non-IdP tokens too (§1.6); optional issue-time claims via `getAccess` are defense-in-depth, not the mechanism of record (stale until re-login, `TOKEN_TTL_SECONDS`).
- **Even a populated `teamIds` is not enough for expense:** `loadReportResource` never sets `resource.teamId` (`expense-report.controller.ts:243-253`), so the team clause has nothing to compare against. `expense_reports.team_id` exists on the model (`apps/expense/src/models/expense-report.model.ts:29`) — the resource loader needs a one-line extension (and should set `tenantId` while there, §1.5).
- **List routes are structurally outside `checkRowScope`:** resource-less requests pass by design ("row filtering for list endpoints is compiled into query predicates + RLS", `scope.ts:10-12, 19-21`). The only list predicate in the codebase is expense's `rowScopeSubmitterFilter()` (`expense.service.ts:1008-1014`, used at :338) — **role-name-based** (Admin/Owner/Manager/Approver ⇒ see all; else own rows) and ignoring `principal.scope`/`teamIds` entirely. Fixing attributes alone will never scope lists; a shared scope-to-WHERE compiler is a separate effort (§4 note 2).
- **Fail-open fall-through:** `checkRowScope` returns `{ok: true}` for any unrecognized scope value (`scope.ts:40`). Adding a new `Scope` enum member without updating this function silently grants. Add an exhaustive-switch or default-deny (§6).
- **Consistency bug in waiting:** a `scope=own_only` principal holding the Manager role sees *all* rows on list routes (role check) but only own rows on single-resource routes (scope check). Reconcile when building the scope compiler.

## 5. Step-by-step implementation plan (phased, expense-first, each phase shippable)

**Phase 0 — Mapper + port interfaces + write-time hardening (no behavior change).** In `libs/access-control`: pure `PolicyRow → PolicyRule | MappingError` mapper with the `rule` envelope validation (§3 Q1 — including `scope` rejection and `$attr` syntax validation), `PolicyReadPort` + `AttributeReadPort` interfaces, unit tests (valid/invalid permission, malformed rule ⇒ MappingError, **all-or-nothing load semantics for both effects**, empty-conditions semantics, is_active filtering, priority-then-id sort). In user-management: extend the PAP validators per Q2 (permission enum, envelope, wildcard-allow ban, scope ban) and run the **one-time audit** of persisted rows. Ships dormant; no route touched.

**Phase 1 — DB loader on expense approve, resource-only literal policy (proves the DB path WITHOUT the PIP or `$attr`).** Implement `dbPolicies(action)` + the shared-DB `PolicyReadPort` default implementation (raw RLS-scoped SELECT per Q6 option (a)); add `registerAccessControlPorts()` to **expense's** bootstrap (`apps/expense/src/bootstrap.ts`, beside `getApprovalContext()` at :31-32) — user-management's too, for its own future consumption. Wire `combinePolicies(dbPolicies(...), amountCapPolicies(...))` on the two expense approve routes (`expense-report.controller.ts:91, :119`) behind a feature flag. Seed a `deny approve when resource.amount gt X` policy — uses `resource.amount`, which the resource loader **already populates** (:251), so no principal attribute is needed. Run §3 Q9 test 1; verify the loader-failure path surfaces as 5xx (Q4). Direct DB read on every evaluation is acceptable at this traffic (one indexed query); cache comes in Phase 3.

**Phase 2 — THE PIP (the load-bearing prerequisite from §0), per the full Q10 spec.** Populate `principal.attributes`:
- Add the `AttributeReadPort` hook in `authorizeAny` (after Gate 1, before the `resource:`/`policies:` loaders, gated on those options being present — `pep.ts:272-274`); this is the project's one deliberate Phase-2 PEP change.
- Default impl: shared-DB batched read of `team_members` (`teamIds`) per Q10; per-(tenant,user) cache, TTL 30–60s; **document the TTL as the team-revocation bound** and add the `abac:attrver:{tenant}:{user}` post-commit bump from team-membership CRUD in user-management (in-phase if tractable, else fast-follow).
- `approvalLimit`: first create its source of truth (column on the user/role assignment, or tenant config — a product decision), then surface via the same port.
- Optionally also stamp issue-time claims via `getAccess` for defense in depth (`user-management.shape.ts:478-485`; `user.repository.ts:95-112`) — never as the only mechanism (§1.6 non-IdP tokens).
- Extend `loadReportResource` to set `resource.teamId` (`expense-report.controller.ts:243-253`; model field exists at `expense-report.model.ts:29`) and `resource.tenantId` (making PDP tenant-iso live on expense, §1.5).
**This phase is what turns `amountCapPolicies` and `own_and_team` from silent no-ops into real gates.** Exit tests: `own_and_team` grants a teammate and denies a stranger; **team removal stops granting within the documented bound** (TTL or version bump); the hardcoded helper now actually denies over-cap.

**Phase 3 — Versioned cache + write-path invalidation.** Redis versioned keys (`abac:polver` + `abac:pol:...:v{n}` + wildcard bucket, negative caching, short TTL — §3 Q4). PAP-side post-commit `INCR` from `PolicyService` for every effective-policy transition, old+new keys on permission rename (capture the pre-update permission via the repository, §3 Q5). Fail-closed ladder (Redis→DB→throw⇒5xx). Soak test: create/patch/deactivate/delete take effect on the next request after the INCR; **the concurrent write+read race test must assert a raced stale SET is never served** (it lands on a dead version key), not merely "no permanently-stale key"; kill the INCR ⇒ converges ≤ TTL (the signed-off residual window).

**Phase 4 — `$attr` + environment + obligations + broaden adoption.** (a) **Cross-attribute capability (gates Phase 5):** loader-side `$attr` interpolation in `dbPolicies` per §3 Q3, fail-closed default + `missing: skip` knob, cached rules stay raw. (b) PEP passes `environment: {time, ip}` into the PDP request (`pep.ts:283-284` change) — unlocks time-window policies (§3 Q3). (c) PDP returns obligations from matching allow rules (fixing the dead code at `pdp.ts:53/94/99`; consumer already waits at `pep.ts:288`). (d) Adopt `dbPolicies` on **invoice approve** and **payroll sensitive read** per §3 Q9 — each is a from-scratch resource loader + bootstrap registration + rollout care for the Gate-2 activation / stale-token effect (`pdp.ts:24`; §1.2).

**Phase 5 — Retire the hardcoded helper (BLOCKED on Phase 4(a); only at proven matrix parity).** Preconditions, in order: (1) the `$attr` capability is live — without it no persisted rule can express the per-approver cap and parity is unachievable by construction (§3 Q3); (2) the no-cap semantics decision is signed off (`missing: skip` mirrors the helper; `fail` is stricter — product call); (3) the Q9 **matrix** parity harness (multiple (limit, amount) pairs, no-cap, NaN-amount) passes helper-only vs DB-only vs both in prod for the parity window. Only then drop the `amountCapPolicies` leg. Keep the helper source until then — it is the reference implementation and the rollback path (§7).

## 7. Non-goals / what NOT to do

- **Do NOT let an LLM/agent author, approve, or mutate policies.** The PAP stays human/admin-gated behind `Permission.PolicyManage` (`policy.controller.ts:21-37`). Agents may *read* effective policy for explanation; policy writes remain a governed admin action.
- **Do NOT bypass RLS.** Every policy read (and everything else) runs in RLS-scoped transactions (`libs/db/src/rls.ts:38-54`; `0028:111-117`). The Redis cache is a performance layer, never a tenant boundary.
- **Do NOT register the policy/attribute read ports in only one service.** Aegis is one process per service (§1.1); `dbPolicies` and the PIP execute in the **consuming** service's process, and an unregistered port fail-closes into a 100% block of the wired routes. Every consuming bootstrap calls `registerAccessControlPorts()` (§2.2, Q6).
- **Do NOT conflate ABAC `policies` with `approval_policies`** — different tables, columns, owners, and purposes (authorization vs approval-chain routing; §4 note 6). Also do not "unify" the three colliding `PolicyRow` type names (`UserManagementShape` / `ApprovalShape` / `ReportingShape`) — they are unrelated concepts sharing a word.
- **Do NOT remove `amountCapPolicies` until the DB path is proven at matrix parity in production — which requires the `$attr` cross-attribute capability first** (§3 Q3, §5 Phases 4-5). A literal-value rule cannot express a per-approver cap; retiring the helper on a fixed-threshold "parity" test would silently regress amount caps. The helper is the reference implementation and the rollback path; `combinePolicies` exists precisely to run both.
- **Do NOT introduce first-match-by-priority PDP semantics opportunistically** (§3 Q8). Deny-overrides is the current, safe, order-independent contract (`pdp.ts:34-38`); precedence semantics are a deliberate, separately-tested v2 if ever.
- **Do NOT ship write-accepted, never-read policy fields.** `PolicyRule.scope` is consumed by nothing in the runtime (§1.2) — reject `scope` in the v1 envelope at the PAP validator *and* the mapper (§3 Q1); the same discipline applies to any future envelope key until the PDP actually consumes it.
- **Do NOT ship wildcard-action *allow* policies in v1** — `decide()` ignores `'*'` allows while `evaluateAbac()` honors them (`pdp.ts:47` vs `:93`); the same policy would behave differently per token shape. Enforce the ban at **write time** plus the one-time data audit — **never by silently filtering at load** (a silently dropped allow un-gates the route, §3 Q8). Wildcard *deny* is consistent and fine.
- **Do NOT reuse `POLICY_RELOAD_CHANNEL` for ABAC invalidation** — it means "reload the Casbin enforcer" (`watcher.ts:30`; sole publisher `pep.ts:201`). v1 needs no pub/sub at all (versioned shared-Redis keys, §3 Q4/Q5); if a per-pod L1 ever lands, use a dedicated ABAC channel and budget the real watcher rework (payload parsing, multi-channel dispatch, startup retry — `watcher.ts:52-88, :100`).
- **Do NOT import oe_core's mechanics** (§1.7): no per-request enforcer/adapter construction (`oe_core RBAC.ts:24-45,71-72`), no global-`'*'` domains, no ordinal role matrices in migrations (`seeders/0034:13-18`), no live enforcer calls inside migrations, no copy-pasted per-endpoint access SQL, no raw string interpolation of ids into queries (`job-access-queries.ts:89-101`), no role special-casing in middleware code. Borrow its *product concepts* only (visibility-level templates, reviewer escape hatch as a policy condition, display-name permission catalog).
- **Do NOT treat loader/cache failures as "no policies" — and do NOT dress them as 403s.** An empty `PolicyRule[]` is a *semantic* state (RBAC alone decides); an *error* must block the request (§3 Q4, §6) and surfaces as **5xx** through the existing error pipeline (`pep.ts:294-296`; `error.middleware.ts:31-33, :53`) — fail-closed for the caller, honest for ops. Conflating errors with emptiness converts outages into authorization bypasses; conflating them with denials corrupts triage.
